# 第三章：MCP 安全

对应原文：[02-Security/README.md](/Users/harvey/Desktop/github/mcp-for-beginners/02-Security/README.md)

这一章的核心不是教你“怎么把系统做得绝对安全”，而是让你先建立一个重要认知：

`MCP 带来了更强的模型-工具连接能力，但也把 AI 系统的攻击面显著放大了。`

如果前两章是在讲：

- MCP 为什么存在
- MCP 由什么组成

那么这一章讲的是：

- 这些组成部分会怎么被攻击
- 哪些风险是 MCP 特有或被放大的
- 安全控制应该放在哪些层

## 1. 为什么安全被放在这么靠前的位置

原文一开始就强调，安全是 AI 系统设计的基础，而且这与 Microsoft 的 `Secure by Design` 原则一致。

这不是形式上的“安全章节”，而是因为 MCP 和普通软件相比，有两个显著不同：

1. 它把模型和外部工具、数据、身份系统连起来了
2. 模型本身会解释文本、上下文和工具描述，这会带来 AI 特有攻击面

所以 MCP 的风险不是只来自传统漏洞，还来自“模型会被诱导、被误导、被投毒”。

## 2. 这一章的总主线

你可以把第三章压缩成一句话：

`MCP 安全 = 传统软件安全基础 + AI 特有攻击防护 + 最小权限和可审计治理。`

也就是说，不能只做下面任何一项：

- 只做 OAuth，不管 prompt injection
- 只防 prompt injection，不做权限管理
- 只做代码安全，不管 token 管理

真正有效的方式是多层防御。

## 3. MCP 主要风险有哪些

原文重点列出了一批高风险问题，包括：

- Prompt Injection
- Tool Poisoning
- Session Hijacking
- Confused Deputy
- Token Passthrough
- Excessive Permissions
- Supply Chain Attacks
- Dynamic Capability Modification

这些名字先不用死记，你先理解它们分别在破坏什么。

### Prompt Injection

攻击者把恶意指令藏在文档、网页、邮件、数据库内容里，让模型把这些内容误当成应该执行的指令。

这类攻击危险的地方在于：

- 恶意内容看起来像普通数据
- 模型会“读懂”这些内容
- 一旦模型把它当作高优先级指令，可能会泄露数据或调用危险工具

所以它不是传统 SQL 注入那种“程序解析错误”，而是“模型被文本诱导”。

### Tool Poisoning

这类攻击不是污染用户输入，而是污染 `tool metadata`，例如：

- 工具描述
- 参数定义
- 示例说明

模型会读这些元数据来决定是否调用某个工具。如果这些描述被恶意修改，模型就可能被引导去做危险操作。

这类攻击的关键点是：

`攻击者不一定改工具代码，只要改工具的“说明书”，就可能误导模型。`

### Session Hijacking

如果 MCP 实现里有会话状态，攻击者一旦拿到 session ID，就可能伪装成合法用户继续调用 server。

风险包括：

- 冒用身份
- 注入恶意事件
- 恶意恢复会话

它本质上仍然是经典会话劫持，但在 MCP 里后果会更重，因为会话可能关联工具权限和上下文状态。

### Confused Deputy

这是一个经典安全问题。简单说就是：

`服务器本身有权限，但被攻击者诱导，替攻击者去做了本来不该做的事。`

在 MCP 中，这常见于认证代理场景，比如 server 代客户端去和第三方身份或资源系统交互，结果被利用完成未授权访问。

### Token Passthrough

这是原文特别强调的危险反模式。

所谓 token passthrough，就是 MCP server 不做正确验证，直接拿客户端给的 token 去访问下游 API。

问题非常严重，因为这会导致：

- 绕过 server 自己的安全控制
- 审计日志失真
- 权限边界混乱
- 被盗 token 可被 server 当代理用来偷数据

原文明确说：

`MCP server 不应接受那些不是明确签发给它自己的 token。`

### Excessive Permissions

也就是权限给得太大。

比如一个只需要查只读知识库的 server，却拿到了：

- 写数据库权限
- 管理员 API 权限
- 广泛文件系统访问权限

一旦被滥用，影响范围会非常大。

### Supply Chain Attacks

这不仅是传统依赖包风险，在 AI 场景里还扩展到：

- foundation model 来源
- embedding 服务
- 第三方 API
- 上下文提供者
- 训练数据来源
- 模型权重和配置

也就是说，AI 系统依赖链比普通应用更长、更复杂。

## 4. OWASP MCP Top 10 要表达什么

原文提到了 OWASP MCP Top 10，包括：

- Token 管理错误
- 权限范围膨胀
- Tool Poisoning
- 供应链攻击
- 命令注入
- Prompt Injection
- 认证授权不足
- 缺少审计和遥测
- Shadow MCP Servers
- Context Injection 和过度共享

你不需要现在就背编号，但要理解它的作用：

`它是在告诉你，MCP 安全问题不是零散的“技巧集合”，而是一套可以系统化识别和治理的风险模型。`

## 5. 为什么 Prompt Injection 在 MCP 里尤其危险

这一章特别强调 `Indirect Prompt Injection`，也就是“间接提示注入”。

这比用户直接输入恶意提示更隐蔽，因为恶意内容可能来自：

- 文档
- 网页
- 邮件
- 数据库
- API 返回值

模型在处理这些外部内容时，可能把其中的隐藏指令一起吞进去。

危险之处在于：

- 内容来自“看似可信”的外部源
- 工具调用可能基于这些被污染的上下文做决策
- 用户甚至不知道哪段文本是攻击载荷

所以 MCP 不是“工具安全”就够了，还要保证：

`提供给模型的上下文本身不能轻易劫持模型行为。`

## 6. Tool Poisoning 为什么特别像“骗模型看错说明书”

Tool Poisoning 的重点不是破坏函数本身，而是破坏模型对工具的理解。

例如一个工具本来应该是：

- 查询产品
- 获取天气
- 发送通知

但如果它的描述、参数说明、示例文本被嵌入了恶意指令，模型可能会：

- 错选工具
- 误传参数
- 在不该执行时执行

对于远程托管的 MCP server，这个风险更高，因为工具元数据可以在用户首次批准后被动态修改，也就是文中说的 `dynamic capability modification` 或者类似 “rug pull” 风险。

这带来一个很重要的工程启发：

`安全检查不能只看第一次连接时的工具列表，还要监控后续变化。`

## 7. 身份认证和授权是 MCP 安全的底盘

原文专门有一大部分讲认证和授权，这说明它仍然是最基础的一层。

重点包括：

- 认证逻辑不能配置错
- token 必须正确验证
- 权限范围必须最小化
- 审批和授权边界必须清晰

### 这部分你最应该记住三点

#### 第一，最小权限原则

只给 server 执行当前任务所需的最小权限。

例如：

- 只读就不要给写权限
- 只访问单个目录就不要给整个磁盘权限
- 只访问一个业务 API 就不要给整套平台管理员权限

#### 第二，token 必须验证 audience 和生命周期

不是拿到 token 就算安全，要确认：

- 这个 token 是不是发给当前 MCP server 的
- 有没有过期
- 能不能被重放
- 是否被错误地转发到下游

#### 第三，server 不能把 session 当认证本身

会话只是会话，不等于授权证明。  
原文强调：有授权要求的 server 必须验证所有入站请求，而不能只依赖 session。

## 8. Token Passthrough 为什么被明确禁止

这一点值得单独记住。

MCP 当前规范明确反对 token passthrough，因为它会破坏三件关键事情：

1. `安全控制`
2. `审计归因`
3. `信任边界`

如果一个 server 只是拿客户端 token 去访问下游 API，就等于：

- server 自己没真正承担认证责任
- 下游看不清真实调用关系
- 整个链路更难做限流、审计、检测和追责

所以正确思路不是“把用户 token 一路传下去”，而是：

`让每个服务在自己的信任边界里完成正确认证和授权。`

## 9. Session Hijacking 和 Confused Deputy 本质上都在破坏“代理关系”

这两个问题虽然形式不同，但都和“代理”有关。

### Session Hijacking

是攻击者抢走你的会话身份，直接冒充你。

### Confused Deputy

是攻击者没直接抢身份，但骗一个本来有权限的服务替他做事。

MCP 的系统天生有代理关系：

- Host 代理用户
- Client 代理 Host 与 server 通信
- Server 代理访问工具和下游系统

所以一旦这些代理链条的身份、权限、重定向、会话绑定做得不严密，就容易出问题。

## 10. 供应链安全在 AI 系统里更大

原文把供应链安全扩展得很完整。它不只是：

- npm 包
- pip 包
- Docker 镜像

还包括：

- 基础模型
- embedding 服务
- 上下文源
- 第三方 AI API
- 模型权重
- 训练或微调数据

这说明在 MCP 场景里，“我依赖了什么”本身就是一个安全问题。

你要形成一个意识：

`任何能影响模型行为、工具行为或上下文质量的外部组件，都属于安全边界的一部分。`

## 11. 微软方案在这一章里扮演什么角色

原文多次提到微软提供的几类安全能力，例如：

- Prompt Shields
- Azure Content Safety
- GitHub Advanced Security
- Entra ID
- Key Vault
- Azure Monitor / Application Insights

你可以把它们分成几类理解：

### 模型输入与内容防护

- Prompt Shields
- Azure Content Safety

用来识别和隔离 prompt injection、越狱、恶意内容、敏感内容。

### 身份和密钥管理

- Entra ID
- Key Vault

用来做认证授权、令牌管理、密钥保护。

### 代码与供应链安全

- GitHub Advanced Security

用来做 secret scanning、依赖扫描、静态分析等。

### 可观测性与审计

- Azure Monitor
- Application Insights

用来做日志、监控、检测、追踪。

## 12. 这一章的防御思路应该怎么记

你可以把第三章的安全策略记成五层：

1. `身份层`
   - 正确认证
   - 正确授权
   - 最小权限

2. `输入层`
   - 输入验证
   - 提示注入检测
   - 内容边界隔离

3. `工具层`
   - 工具元数据校验
   - 工具变更监控
   - 高风险工具确认机制

4. `会话与传输层`
   - HTTPS
   - 安全 session ID
   - 过期与轮换
   - 防重放

5. `审计与供应链层`
   - 日志
   - 依赖扫描
   - 组件来源验证
   - 快速回滚与响应

如果这五层你能记住，后面看具体实现就不容易乱。

## 13. 学完这一章后，你最应该掌握什么

学完第三章，不是要你立刻成为安全专家，而是要你具备下面这些判断力：

1. 一个 MCP 系统的风险不只是“工具代码有 bug”
2. 模型读到的文本本身也可能是攻击载荷
3. 工具描述和元数据也会成为攻击入口
4. token、session、权限边界必须严格治理
5. AI 系统的供应链远比普通应用更复杂

如果你能形成这些判断，这章就学到了核心。

## 14. 常见误区

- 误区一：做了 OAuth 就算安全
  - 不对。Prompt injection、tool poisoning、供应链风险依然存在。
- 误区二：只要工具代码安全，模型就不会被利用
  - 不对。模型可能被上下文和工具元数据误导。
- 误区三：session 能代表认证
  - 不对。session 不能替代每次请求应有的授权验证。
- 误区四：把用户 token 传给下游最省事
  - 这是高风险反模式，规范明确反对。
- 误区五：供应链安全只和依赖包有关
  - 不对。模型、数据源、第三方 AI 服务都属于供应链。

## 15. 一句话总结

`第三章的核心不是“多记几个漏洞名称”，而是理解 MCP 会把模型、上下文、工具、身份和外部服务连成一条链，而安全工作的本质就是保证这条链上的每一环都不会被轻易滥用、误导或劫持。`
