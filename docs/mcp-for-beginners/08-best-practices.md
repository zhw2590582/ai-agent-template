# 第九章：Best Practices

对应原文：[08-BestPractices/README.md](/Users/harvey/Desktop/github/mcp-for-beginners/08-BestPractices/README.md)

这一章的重点不是再教你新功能，而是把前面学过的内容收束成一套“怎么把事情做对”的原则。

如果说前几章更多在回答：

- MCP 是什么
- 怎么实现
- 能用到哪里

那么这一章回答的是：

`一个好的 MCP Server 应该如何被设计、测试、运行和维护。`

## 1. 这一章为什么重要

很多系统不是死在“不会做”，而是死在“做得不规范”。

MCP 也一样。  
一个能工作的 server，不一定是一个好的 server。

常见问题包括：

- tool 设计过大过杂
- 参数校验不严
- 错误信息混乱
- 缺少日志和监控
- 没有取消机制
- 安全边界含糊

这一章的价值，就是帮你把这些“经验教训”提前内化。

## 2. 这一章的主线

原文把最佳实践分成两个大方向：

- 安全最佳实践
- 实现最佳实践

这说明 MCP 的成熟实践不是只关心代码风格，而是同时关心：

- 用户控制
- 安全边界
- 协议行为
- 工具设计
- 可观测性
- 运行可靠性

## 3. 核心原则有哪些

原文列出了五个核心原则：

1. 标准化通信
2. 用户中心设计
3. 安全优先
4. 模块化架构
5. 有状态连接

这五个原则可以这样理解。

### 标准化通信

不要把 MCP 当成“随便传点 JSON 就行”，而要认真遵守协议约定。  
这样系统才具有互操作性和可维护性。

### 用户中心设计

用户应该清楚：

- 系统在访问什么
- 要执行什么操作
- 哪些工具会被调用

也就是说，用户控制和透明度不是附加项。

### 安全优先

安全不是出了问题再补，而是工具设计、参数校验、权限控制的一部分。

### 模块化架构

一个工具做一件事，一个资源负责清晰边界，一段提示模板服务明确场景。  
不要把所有功能糊成一个“万能工具”。

### 有状态连接

MCP 支持状态性，这意味着你可以构建更连贯的交互，但也意味着你要认真管理会话和上下文。

## 4. 这一章最有价值的一点：Tool 设计原则

原文反复强调：

`让每个 tool 专注做好一件事。`

这其实就是单一职责原则在 MCP 里的体现。

为什么重要？

因为一个设计良好的 tool 更容易：

- 被模型理解
- 被客户端发现
- 被用户授权
- 被独立测试
- 被独立审计

相反，过于庞杂的 tool 会带来：

- 模型误用
- 参数复杂
- 错误边界不清
- 难以维护

所以写 MCP tool 时，最重要的问题之一不是“还能不能多塞点功能”，而是：

`这个 tool 的职责是不是已经太宽了。`

## 5. 参数校验为什么是刚需

原文专门强调 parameter validation。  
这不是形式主义，而是因为 MCP tool 是模型会直接参与调用的接口。

如果不严格校验，就容易出现：

- 参数缺失
- 类型错误
- 危险输入
- 越权路径
- 注入风险

所以参数 schema 不只是为了文档好看，它其实是：

`工具安全边界和可靠性边界的一部分。`

## 6. 错误处理为什么必须统一

原文强调 standardized error handling，这一点非常关键。

好的错误处理应该做到：

- 错误信息足够清楚
- 能区分客户端问题和服务端问题
- 能帮助调试
- 不泄露不该暴露的细节

对 MCP 来说，错误处理尤其重要，因为错误可能发生在：

- transport
- 协议层
- 参数校验
- 工具执行
- 下游 API

如果错误风格混乱，整个系统会非常难排查。

## 7. Logging、Progress、Cancellation 为什么是成熟度标志

原文把这几个点放在最佳实践里，说明它们是生产级系统的重要特征。

### Logging

日志是为了：

- 调试
- 审计
- 监控
- 事故分析

没有日志，MCP 系统一旦进入复杂工具链，就会很难定位问题。

### Progress Tracking

长任务如果没有进度反馈，用户体验会很差，客户端也很难知道是否还在工作。

### Request Cancellation

当用户不再需要某个结果时，系统应该允许取消，避免浪费资源。

这三个能力合在一起，体现的是：

`一个 MCP 实现有没有把“运行中的真实体验和真实成本”考虑进去。`

## 8. 这一章和前面安全章节的关系

第二章讲安全风险模型，这一章则更像是在说：

“好，那你现在知道风险了，开发时应该怎么规避？”

例如这里再次强调：

- 用户同意
- 数据隐私
- 工具安全
- 工具权限控制
- 认证
- 参数校验
- 限流

这说明最佳实践并不是抽象建议，而是安全原则在工程中的具体化。

## 9. 学完这一章后应该形成什么习惯

你应该逐渐养成以下开发习惯：

1. 先想 tool 边界，再写代码
2. 先想参数校验，再开放调用
3. 先想错误和日志，再谈集成
4. 先想用户同意和权限边界，再接敏感数据
5. 先想取消、进度、超时，再处理长任务

这几个习惯比“多记几个 API”更重要。

## 10. 一句话总结

`这一章的核心，是让你从“会做 MCP”升级到“会把 MCP 做得规范、可靠、安全、可维护”。`
