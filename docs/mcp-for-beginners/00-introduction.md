# 第一章：MCP 导论

对应原文：[00-Introduction/README.md](/Users/harvey/Desktop/github/mcp-for-beginners/00-Introduction/README.md)

这一章的目标不是立刻写 MCP 程序，而是先建立一个正确的全局认知：MCP 到底是什么，为什么它重要，它解决了什么问题，它的基本架构长什么样。

你可以先记住一句话：

`MCP 是让大模型连接外部工具和数据的一套标准接口。`

## 1. 什么是 MCP

仓库原文把 MCP 定义为一个开放、标准化的接口，用于让大语言模型和外部工具、API、数据源协同工作。

这里要抓住三个关键词：

1. 开放
2. 标准化
3. 模型和外部能力之间的接口

这意味着 MCP 不是某个单独产品，也不是某家厂商私有的插件机制，而是一套约定好的通信方式。

可以把它类比成：

- HTTP 之于浏览器和服务器
- SQL 之于应用和数据库
- USB-C 之于设备连接

MCP 的核心价值不在于“新增了一个工具”，而在于：

`它统一了模型访问工具的方式。`

## 2. 为什么标准化重要

这一章最核心的观点是：AI 应用前期很容易做起来，但随着功能增多、模型增多、工具增多，系统会迅速变复杂。这时候如果没有统一标准，系统会越来越难维护。

没有标准化时，常见问题包括：

- 每个模型接一个工具都要单独写代码
- 不同供应商的 API 风格不同
- SDK 升级后原有集成容易失效
- 工具越多，维护成本越高

这就是原文提到的碎片化问题。MCP 的意义，就是把这些零散、脆弱、一次性的集成方式，变成统一、可扩展的架构。

## 3. MCP 解决了什么问题

原文列出了四个核心收益：

- `Interoperability`：互操作性
- `Consistency`：一致性
- `Reusability`：可复用性
- `Accelerated Development`：加速开发

可以这样理解：

- 互操作性：不同模型、工具、平台更容易协同
- 一致性：工具暴露给模型的方式更统一
- 可复用性：一个 MCP Server 可以被多个宿主或项目复用
- 加速开发：不用每次都从零写一套专用集成

所以 MCP 解决的不是“模型能不能调工具”，而是：

`模型怎样以可扩展、可维护、可复用的方式去调工具。`

## 4. MCP 的基本架构

这一章给出的架构是客户端-服务器模式，里面有三个核心角色：

- `MCP Client`
- `MCP Host`
- `MCP Server`

先用最直白的方式理解：

- Client：请求入口，比如 IDE、聊天界面、桌面应用
- Host：总控中心，负责运行模型并协调 MCP 通信
- Server：能力提供方，负责暴露工具、资源、上下文

很多初学者容易把 Client 和 Host 混掉。更准确地说：

- Client 更像“用户接触到的应用入口”
- Host 更像“背后的调度和治理层”

## 5. 一次请求是怎么走的

根据原文流程，一次典型请求大致如下：

1. 用户或软件发起请求
2. `MCP Client` 把请求发送给 `MCP Host`
3. `MCP Host` 中运行的模型处理用户输入
4. 模型发现需要某个外部工具或数据
5. `MCP Host` 通过 MCP 协议联系合适的 `MCP Server`
6. `MCP Server` 执行操作并返回结果
7. `MCP Host` 整理结果并交给模型
8. 模型基于这些结果生成最终回复
9. `MCP Client` 把结果展示给用户

这里最重要的一点是：

`不是模型直接连接工具，而是 Host 负责协调模型和 Server 的通信。`

## 6. 为什么 Host 很关键

原文指出，Host 通常负责以下几类工作：

- `Tool Registry`：记录有哪些工具和能力
- `Authentication`：鉴权和权限验证
- `Request Handler`：处理工具调用请求
- `Response Formatter`：把工具输出整理成模型可消费的格式

所以 Host 不只是消息转发器，它更像 MCP 架构里的治理层。

这意味着 MCP 的重点不只是“让模型接工具”，而是：

`让工具接入进入一个可治理、可审计、可扩展的体系。`

## 7. MCP 中的核心能力对象

这一章先引入了几个后续会展开的概念：

- `Resources`
- `Prompts`
- `Tools`
- `Sampling`
- `Elicitation`
- `Roots`

你先建立一个初步印象即可：

- Resources：给模型读取的数据
- Prompts：预定义的提示模板或工作流
- Tools：可执行函数
- Sampling：支持更智能、递归式的代理行为
- Elicitation：服务器主动请求更多用户输入
- Roots：文件系统访问边界，和安全相关

这说明 MCP 不只是工具调用协议，它还规范了资源访问、交互方式和边界控制。

## 8. MCP 的两层结构

原文还提到 MCP 的两层架构：

- `Data Layer`
- `Transport Layer`

可以这样理解：

- Data Layer 负责“消息内容怎么定义”，基于 `JSON-RPC 2.0`
- Transport Layer 负责“消息怎么传输”，例如：
  - `STDIO`
  - `Streamable HTTP with SSE`

也就是说：

- Data Layer 解决“说什么”
- Transport Layer 解决“怎么送过去”

## 9. 这一章的两个关键类比

### 类比一：MCP 像 AI 世界里的 USB-C

意思是你不希望每个模型和每个工具之间都要发明一套新接口。MCP 试图成为统一连接标准。

### 类比二：知识和动作都能统一暴露

MCP 不只支持执行动作，也支持提供知识上下文。比如：

- 一个 server 提供文档检索
- 一个 server 提供数据库查询
- 一个 server 提供发送邮件

从 agent 的视角看，这些都是“可以调用的能力”。

## 10. 真实应用场景

第一章列出的典型场景包括：

- 企业数据集成
- Agentic AI 系统
- 多模态应用
- 实时数据接入

这些场景的共同点是：

`模型必须超越纯文本生成，开始连接外部环境并采取动作。`

而 MCP 正是支持这一点的标准协议。

## 11. 学完这一章，你应该会什么

学完后，至少应该能回答以下问题：

1. MCP 是什么？
2. 为什么 AI 系统需要标准化的模型-工具通信方式？
3. MCP 里 Client、Host、Server 各自负责什么？
4. 一次 MCP 工具调用的完整流程是什么？
5. MCP 为什么适合做可扩展 AI 系统的基础设施？

如果你能用自己的话说出下面这段，就说明主干已经掌握：

`MCP 是一个让大模型以标准方式访问工具、资源和外部系统的开放协议。它通过 Host、Client、Server 的分层协作，把原本零散的模型-工具集成变成统一架构，从而提升扩展性、维护性、复用性，并减少对单一厂商方案的绑定。`

## 12. 常见误区

- 误区一：MCP 就是工具调用
  - 不完整。它还包括 resources、prompts、sampling、elicitation、roots 等能力。
- 误区二：模型直接连 server
  - 不准确。通常是 Host 负责与 MCP Server 通信。
- 误区三：MCP 只是为了方便开发
  - 不止。它更深层的价值是架构治理和生态兼容。
- 误区四：有了 MCP 就完全不用适配
  - 也不对。它减少的是重复造轮子，不是消灭所有业务差异。

## 13. 学习建议

学完这一章，先不要急着背术语。建议优先做两件事：

1. 彻底分清 `Host / Client / Server`
2. 能用自己的话解释“为什么标准化重要”

如果这两点搞清楚了，后面学习第二章 `01-CoreConcepts` 会轻松很多。
